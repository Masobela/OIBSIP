========================================
6. FINDINGS
========================================
OBSERVED
- Normal input "1" returned one record.
- The input "1' OR '1'='1" returned five records.
- The same input field and the same page were used in both tests.
- The injected input appears in the page address as id=1'+OR+'1'%3D'1.
- The page shows only first name and surname for each record.

INTERPRETATION (NOT DIRECTLY OBSERVED)
- The always-true condition '1'='1 changed the behaviour of the
  vulnerable query, so it matched every row instead of one.
- This is consistent with user input being placed into the SQL query
  without safe handling at the Low level.
- The query source code was not shown, so the exact query is unknown.

NOT TESTED
- Medium, High and Impossible security levels.
- Any other payload or technique.
- Any other table or column.

========================================
7. REMEDIATION NOTE
========================================
- Use prepared statements (parameterized queries) so that user input is
  treated as data and never as SQL code.
- Also validate input (for example, accept numbers only for an ID) and
  use a database account with minimum permissions.

========================================
8. CONCLUSION
========================================
At Low security, DVWA returned one record for the normal input "1" and
five records for the payload "1' OR '1'='1". The always-true condition
altered the behaviour of the vulnerable query. Parameterized queries
(prepared statements) are the main fix.

Scope: deliberately vulnerable app in an isolated local lab, for
educational and training purposes only.
